# Код-ревью: DSP Flow — блоки и диалоги параметров

**Дата:** 2026-02-24
**Ветка:** `fix/block_param_edit`
**Тесты:** 151/151, ESLint: без новых ошибок

---

## 1. Исправленные проблемы (в этой ветке)

### 1.1. Отсутствующие параметры в специализированных фильтрах

**Файлы:** `BandpassFIRPlugin.js`, `LowpassFIRPlugin.js`, `HighpassFIRPlugin.js`

Процессор `createFIRProcessor()` использует параметры `windowFunction` и `designMethod` для расчёта коэффициентов, но в `defaultParams` специализированных фильтров (ФНЧ, ФВЧ, Полосовой) эти параметры отсутствовали. В результате:
- В диалоге редактирования **не было полей** для выбора оконной функции и метода расчёта
- Процессор всегда использовал хардкод-значения (`hamming` и `window`)

**Исправление:** Добавлены `windowFunction: 'hamming'` и `designMethod: 'window'` в `defaultParams` всех трёх плагинов.

### 1.2. Несоответствие имени параметра окна в БПФ

**Файл:** `FFTPlugin.js`

Плагин БПФ использовал имя параметра `windowType`, тогда как в реестре (`initPlugins.js`) опции зарегистрированы под именем `windowFunction`. Из-за этого:
- В диалоге отображалось **текстовое поле** вместо выпадающего списка
- Пользователю приходилось вводить название окна вручную

**Исправление:** Переименовано `windowType` → `windowFunction` в `defaultParams` и в `process()`.

### 1.3. Устаревший лейбл метода расчёта Remez

**Файл:** `initPlugins.js`

Метод Remez Exchange был помечен как «не реализовано, используется Windowed Sinc», хотя полноценная реализация алгоритма Паркс-Макклеллана уже присутствует в `FilterDesign.js`.

**Исправление:** Обновлены лейблы: `'Оконный метод (Windowed Sinc)'` и `'Паркс-Макклеллан (Remez Exchange)'`.

### 1.4. Отсутствующие dropdown-опции для строковых параметров

**Файл:** `initPlugins.js`

Ряд параметров с фиксированным набором допустимых значений отображались как текстовые поля:

| Параметр | Плагин | Добавленные опции |
|---|---|---|
| `constellation` | Фазовое созвездие | BPSK, QPSK, 8PSK, 16-QAM, 64-QAM |
| `outputRange` | Фазовый детектор | ±180°, ±π, 0–360°, 0–2π |
| `normalization` | Сумматор | Без нормализации, Среднее, По пику |
| `operation` | Перемножитель | Умножение, Деление |

### 1.5. Потеря числового типа при select-options

**Файл:** `BlockParamsDialog.jsx`

При выборе значения из dropdown (например, `fftSize`) HTML `<select>` всегда возвращает строку. Обработчик `handleParamChange` не конвертировал значение обратно в число, что приводило к передаче `"2048"` (string) вместо `2048` (number) в параметры процессора.

**Исправление:** Добавлена логика для типа `'select-options'` — если исходное значение было числом, выбранное значение конвертируется обратно в `number`.

### 1.6. Неполные русские переводы параметров

**Файл:** `helpers.js` → `formatParamName()`

Прежняя реализация использовала цепочку `replace()`, что работало некорректно для составных имён. Добавлен словарь точных соответствий для всех параметров блоков.

## 2. Обнаруженные проблемы (требуют отдельного рассмотрения)

### 2.1. Сумматор не реализует нормализацию

**Файл:** `SummerPlugin.js`
**Серьёзность:** средняя

Параметр `normalization` объявлен в `defaultParams`, но в `process()` не используется. При `normalization: 'average'` ожидается деление суммы на количество входов, а при `'peak'` — нормализация к пиковому значению. Текущая реализация всегда возвращает простую взвешенную сумму.

### 2.2. Перемножитель не реализует деление

**Файл:** `MultiplierPlugin.js`
**Серьёзность:** средняя

Параметр `operation` принимает значение `'multiply'`, но в коде нет ветки для `'divide'`. Если добавлять опцию деления в dropdown, нужно реализовать соответствующую логику (с защитой от деления на ноль).

### 2.3. Фазовый детектор — неполная обработка outputRange

**Файл:** `PhaseDetectorPlugin.js`
**Серьёзность:** низкая

Текущий код проверяет наличие символа `°` в `outputRange` для решения, конвертировать ли в градусы. Но:
- Не реализован диапазон `0–360°` (текущий код выдаёт накопленную фазу, которая может быть отрицательной)
- Не реализован диапазон `0–2π`

### 2.4. Спектроанализатор — не используются параметры `frequencyRange`, `dBScale`, `averaging`

**Файл:** `SpectrumAnalyzerPlugin.js`
**Серьёзность:** средняя

Из пяти параметров в `defaultParams` процессор использует только `fftSize` и `windowFunction`. Остальные три (`frequencyRange`, `dBScale`, `averaging`) объявлены, но не участвуют в обработке:
- `frequencyRange: 'full'` — нет обрезки спектра
- `dBScale: true` — всегда возвращает dB (через `computeMagnitudeDB`)
- `averaging: 5` — нет экспоненциального или скользящего усреднения

### 2.5. Осциллограф — параметры `samplingRate` и `channels` не используются

**Файл:** `OscilloscopePlugin.js`
**Серьёзность:** низкая

Процессор просто прокидывает вход. Параметры `samplingRate` и `channels` объявлены в `defaultParams`, но не используются ни в процессоре, ни (предположительно) в компоненте визуализации.

### 2.6. Фазовое созвездие — процессор-заглушка

**Файл:** `ConstellationPlugin.js`
**Серьёзность:** низкая (ожидаемо для визуализации)

Процессор просто прокидывает входной сигнал. Параметры `symbolRate`, `constellation`, `eyeDiagram` не используются в процессоре. Это нормально, если обработка происходит в компоненте визуализации, но стоит проверить, что визуализатор действительно их учитывает.

### 2.7. Скользящее БПФ — нет выбора оконной функции

**Файл:** `SlidingFFTPlugin.js`
**Серьёзность:** низкая

Оконная функция захардкожена как `hanning`:
```js
const windowFn = WindowFunctions.hanning;
```
Нет параметра `windowFunction` в `defaultParams`, хотя другие блоки анализа позволяют его выбирать.

### 2.8. Сумматор — массив `weights` отображается как текстовое поле

**Файл:** `SummerPlugin.js` + `BlockParamsDialog.jsx`
**Серьёзность:** низкая

Параметр `weights: [1.0, 1.0]` — массив, который `typeof` определяет как `'object'`. В результате `getInputType` возвращает `'text'`, и массив отображается как строка `"1,1"`. Редактирование через текстовое поле неудобно и чревато ошибками.

### 2.9. Специализированные фильтры позволяют менять `filterType`

**Файлы:** `BandpassFIRPlugin.js`, `LowpassFIRPlugin.js`, `HighpassFIRPlugin.js`
**Серьёзность:** низкая

В диалоге параметров отображается dropdown `filterType` (ФНЧ/ФВЧ/Полосовой). Пользователь может изменить, например, тип «Полосового КИХ-фильтра» на «ФНЧ», при этом блок на холсте останется с именем «Полосовой КИХ-фильтр». Это вводит в заблуждение. Варианты решения:
- Скрыть `filterType` из редактора для специализированных фильтров
- Или синхронизировать имя блока с выбранным типом

### 2.10. Частотный детектор — не используются `centerFrequency`, `bandwidth`, `sensitivity`

**Файл:** `FrequencyDetectorPlugin.js`
**Серьёзность:** средняя

Из трёх параметров в `defaultParams` процессор использует только `sampleRate` (который берётся из контекста, а не из defaultParams). Параметры `centerFrequency`, `bandwidth` и `sensitivity` объявлены, но не влияют на работу:
- Нет фильтрации по `centerFrequency ± bandwidth`
- Нет масштабирования по `sensitivity`

Текущий процессор вычисляет мгновенную частоту через дифференцирование фазы, что корректно как базовая реализация, но объявленные параметры создают ложное впечатление настраиваемости.

### 2.11. Фильтр Герцеля — `samplingRate` дублирует системный `sampleRate`

**Файл:** `GoertzelFilterPlugin.js`
**Серьёзность:** низкая

Плагин имеет собственный параметр `samplingRate: 48000`, хотя `sampleRate` передаётся через общий контекст params. Если пользователь изменит `samplingRate` в диалоге, а системная частота будет другой, результат будет некорректным.
